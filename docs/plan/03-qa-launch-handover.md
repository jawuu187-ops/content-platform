## 1. ز. استراتيجية الاختبار ومعايير الجاهزية

### 1.1 هرم الاختبار

| الطبقة | ما تغطيه | الأدوات | موضع التشغيل | الحد الأدنى |
|---|---|---|---|---|
| وحدة | منطق الدفتر، العمولة، صلاحية الوصول، صحة التواريخ | Go test، property-based (rapid) | CI | ≥ 80% في `ledger`, `billing`, `entitlements`, `subs` |
| تكامل | PostgreSQL حقيقي، معاملات، outbox، ويبهوكس | testcontainers | CI (service container) | كل مسار مالي |
| تعاقد | OpenAPI vs التنفيذ، محوّلات PSP | schemathesis/kin-openapi | CI | كل مسار `/v1` عام |
| E2E API | رحلات كاملة (تسجيل→اشتراك→PPV→سحب) | Go + httpexpect | CI ليلي | 12 رحلة |
| E2E تطبيق | تدفقات UI على emulator | Maestro + Compose UI test | CI على GitHub runner | 15 تدفقًا |
| أمان | أسرار، تبعيات، SAST، DAST، ASVS | gitleaks، govulncheck، Trivy، CodeQL، ZAP | CI أسبوعي + قبل إصدار | 0 حرج/عالي |
| أداء | API، بحث، بدء الفيديو | k6 | قبل إصدار + شهريًا | p95 API < 300ms |
| كارثة | استعادة نسخة، تعطّل PSP/CDN | سيناريو موثّق | ربع سنوي | RTO < 1س، RPO < 5د |

### 1.2 اختبارات لا يجوز تأجيلها (تمنع كوارث حقيقية)

1. **الدفتر:** لكل journal مجموع مدين = مجموع دائن؛ لا رصيد سالب؛ إعادة الويبهوك لا تُضاعف.
2. **الصلاحيات:** بلا تحقق عمر أو بلا entitlement → 403 + سجل؛ لا استثناء لأي مسار.
3. **الروابط:** رمز منتهٍ/مُعاد استخدامه من جهاز آخر = رفض.
4. **سياسة المحتوى:** المحتوى الصريح → مرفوض آليًا ولا يُنشر بأي موافقة بشرية.
5. **العزل:** مستخدم A لا يستطيع قراءة رسائل/مشتريات B (اختبار IDOR آلي على كل مسار).
6. **المال الحقيقي:** اختبار sandbox كامل قبل أول معاملة إنتاج.

### 1.3 معايير "جاهز للإطلاق" (كلها إلزامية)

- [ ] كل وظائف الجدول 1.1 في الجزء 1 منفذة ومختبرة (لا mock، لا "قريبًا").

- [ ] سياسة محتوى مُنفَّذة تقنيًا + 2257 records pipeline جاهز.

## 2. ح. الإطلاق والتسليم والاستحواذ

### 2.1 ما يجعل المشروع قابلًا للبيع من اليوم الأول

| البند | كيف يُنفَّذ الآن |
|---|---|
| ملكية الكود | كيان قانوني يملك المستودع، لا حساب شخصي؛ ترخيص ملكي واضح (موجود) |
| لا أسرار في الكود | GitHub Secrets + secret store للإنتاج؛ gitleaks في CI |
| لا خدمات مربوطة بحسابك الشخصي | حسابات خدمة (service accounts) لكل مزوّد، مسجلة في `docs/vendors/accounts.md` |
| قابلية النقل | IaC (OpenTofu)، سكربتات نشر، نسخ احتياطي، لا خطوات يدوية غير موثقة |
| توثيق API | OpenAPI 3.1 مُولَّد + أمثلة + Postman collection |
| توثيق قاعدة البيانات | migrations + ERD + وصف كل جدول وحقول الحساسية |
| توثيق معماري | ADRs (موجودة) + مخططات + قرارات مالية |
| سجل التغييرات | `decisions-log.md` + CHANGELOG + وسم الإصدارات |
| إثبات الجودة | تقارير CI، تغطية، نتائج اختبار الاختراق، تقارير حمل |
| تراخيص التبعيات | `docs/legal/dependencies.md` مُولَّد آليًا + منع copyleft في مسار المنتج (ADR-0010) |
| العقود | عقود صنّاع، اتفاقية معالجة بيانات (DPA)، عقود مزوّدين |
| البيانات المالية | بيانات إيراد/هامش/ARPU/churn قابلة للتدقيق — أهم ما يشتريه المستحوذ |

### 2.2 حزمة التسليم (Data Room)

1. `docs/` كاملة: منتج، معمارية، ADRs، أمن، امتثال، تشغيل، مزوّدون.
2. مستودع واحد (أو Monorepo) بصلاحيات نقل مالك واضحة.
3. قائمة الحسابات والاشتراكات وتكاليفها وحالاتها (بدون كلمات مرور).
4. إجراءات النشر والاستعادة واختبار الكوارث.
5. تقارير: تغطية اختبارات، فحص ثغرات، اختبار حمل، اختبار اختراق.
6. ملف الامتثال: 2257، سياسة المحتوى، سجلات التحقق، DPIA، سجل المعالجة.
7. مؤشرات المنتج: MAU، صنّاع نشطون، ARPPU، churn، نسبة الاحتياطي المالي.

### 2.3 تسلسل الإطلاق

1. **بيئة staging** كاملة ببيانات وهمية + PSP sandbox (أسبوع 25).
2. **Beta مغلق**: 10–25 صانعًا موثّقًا، 200–500 مشترك، دفع حقيقي، مراقبة لصيقة (4 أسابيع).
3. **إطلاق مقيّد جغرافيًا**: UK/EU أولًا (سوق دفع + امتثال واضح)، ثم توسّع.
4. **إطلاق عام** بعد اجتياز معايير 1.3 + أول دورة سحب مكتملة.

## 3. تفويض GitHub — الحالة والصلاحيات

### 3.1 الحالة الفعلية (تحققت الآن)

`gh auth status` يُظهر تسجيل دخول نشط إلى `github.com` بالحساب **jawuu187-ops** عبر
GitHub CLI، والصلاحيات الحالية: `repo`, `workflow`, `read:org`, `gist`.
أي أن **التفويض الرسمي موجود مسبقًا** عبر آلية GitHub الرسمية (OAuth device flow الخاص بـ
`gh`)، ولم أطلب منك أي كلمة مرور أو رمز.

### 3.2 ما أحتاجه فعليًا (أقل صلاحيات كافية)

| الصلاحية | لماذا | هل هي مطلوبة |
|---|---|---|
| `repo` | قراءة/كتابة الكود، الفروع، PRs، Releases، Artifacts | نعم |
| `workflow` | إنشاء وتعديل GitHub Actions وتشغيلها | نعم (بدونها لا يمكن إصلاح CI) |
| `read:org` | قراءة معلومات المؤسسة إن كان المستودع داخل org | فقط إن استخدمنا org |
| `gist` | غير مستخدم في هذا المشروع | **غير مطلوبة** — يمكن إزالتها |
| `admin:repo_hook`, `delete_repo`, `packages` | غير مطلوبة | لا |

**لا أحتاج ولن أطلب:** مفاتيح SSH، كلمات مرور، رموز 2FA، أو أي وصول لحسابك البنكي/الدفع.

### 3.3 المطلوب منك (خطوتان فقط)

1. **الموافقة على إنشاء مستودع خاص** باسم مقترح `content-platform` تحت `jawuu187-ops`
   (أو اسم تختاره أنت).
2. **الموافقة على إعدادات الحماية** التي سأفعّلها: حماية `main` (منع force-push، مراجعة PR)،
   Dependabot، secret scanning، CodeQL، والقواعد التي تمنع بناء Android محليًا.

### 3.4 ما لن أفعله دون موافقة منفصلة

- إنشاء مؤسسة (org) أو نقل ملكية المستودع.
- شراء أي خطة مدفوعة (GitHub Team، نطاق، استضافة).
- إضافة أي تعاون أو صلاحيات لمستخدمين آخرين.
- نشر أي شيء علنيًا (المستودع سيبقى خاصًا).

## 4. قواعد العمل التي ألتزم بها

1. لا تغيير لفكرة المشروع أو نموذج العمل.
2. لا اختصار لوظيفة أساسية، ولا واجهة شكلية مكان وظيفة حقيقية.
3. لا بيانات تجريبية تُقدَّم كوظيفة مكتملة.
4. لا تثبيت Android SDK/Studio/Gradle ولا أي بناء APK على Kali — البناء على GitHub فقط.
5. لا مشتريات أو اشتراكات أو تعاقدات نيابة عنك.
6. لا ادعاء اكتمال ميزة دون اختبار يظهر في CI.
7. كل مرحلة تُوثَّق قبل الانتقال.
